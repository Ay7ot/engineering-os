# Triage

Move issues through a small state machine of triage roles. Where the tracker
treats them as a request surface, external PRs are triage work too: a PR is an
issue with attached code, same roles and states, with the deltas noted below.
Resolve a bare `#42` to an issue or PR per the tracker configuration.

Every comment or issue posted during triage must start with this disclaimer:
`> This was generated by AI during triage.`

## When to use
- The maintainer asks what needs attention, or names an issue or PR to triage.
- An issue needs a category, a state, an agent brief, or closing.
- A prior triage needs resuming because the reporter replied.

## Roles
Exactly one category role and one state role per triaged issue. If state roles
conflict, flag it and ask the maintainer before doing anything else.

Categories: `bug` (broken), `enhancement` (new feature or improvement).

States: `needs-triage` (maintainer must evaluate), `needs-info` (waiting on the
reporter), `ready-for-agent` (fully specified, ready for an unattended agent),
`ready-for-human` (needs human implementation), `wontfix` (will not be actioned).
Read a PR's states against its diff: `ready-for-agent` means a brief is attached
and an agent takes the next step; `ready-for-human` means it is ready to merge.

Transitions: an unlabeled issue normally goes to `needs-triage`, then to
`needs-info`, `ready-for-agent`, `ready-for-human` or `wontfix`; `needs-info`
returns to `needs-triage` once the reporter replies. The maintainer may override
at any time, so flag unusual transitions and ask first. Tracker label strings may
differ from these canonical names; ask for the mapping if it was not provided.

## Choose the work
To show what needs attention, query the tracker and present three buckets, oldest
first, each with a count and one line per item. To write the agent brief or the
needs-info notes, and for the bucket definitions, external PR filter and resume
rules, see `references/tracker-conventions.md`.

## Triage one issue or PR
1. **Gather context.** `read` the issue or PR (body, comments, labels, author,
   dates, and the diff) plus any prior triage notes, so resolved questions are
   not re-asked. Explore the codebase with `grep` and `glob` using the domain
   glossary and respecting ADRs. Run two checks: (a) redundancy, search for an
   existing implementation by domain concept rather than by the request's wording
   and report where you looked; if found it is an already-implemented `wontfix`;
   (b) prior rejection, `read` `.out-of-scope/` and surface anything resembling
   this request.
2. **Recommend** your category and state with reasoning, plus a short codebase
   summary including whether it is already implemented. Wait for direction.
3. **Verify the claim** before any grilling: reproduce the bug from the
   reporter's steps, or confirm the PR diff does what it claims. Run the relevant
   tests or commands and report confirmed (with the code path), failed, or
   insufficient detail (a strong `needs-info` signal).
4. **Grill if needed**, one question at a time, sharpening domain terms and
   updating the glossary and ADRs inline as decisions land. Use `brainstorming`
   when the request needs shaping into a design.
5. **Apply the outcome.** `ready-for-agent`: post an agent brief, then apply the
   label. `ready-for-human`: the same brief, plus why it cannot be delegated
   (judgment calls, external access, design decisions, manual testing).
   `needs-info`: post triage notes. `wontfix`: close, with the comment shaped by
   why. Already implemented: point to where it lives and do NOT write to
   `.out-of-scope/` (that knowledge base holds rejected requests, not built ones).
   Rejected bug: a polite explanation, then close. Rejected enhancement: write the
   `.out-of-scope/` entry, link it from a comment, then close. `needs-triage`:
   apply the role, plus an optional comment on partial progress.
6. **Quick override.** If the maintainer says "move #42 to ready-for-agent",
   confirm the role change, comment and close, then act, skipping grilling. With
   no grilling session, ask whether they want a brief written.

## Checklist
- [ ] Disclaimer on every posted comment
- [ ] Exactly one category and one state role applied
- [ ] Redundancy and prior-rejection checks run and reported
- [ ] Claim verified (reproduced, or diff confirmed) before grilling
- [ ] Outcome applied with the correct brief, notes, or close reason
- [ ] `.out-of-scope/` written only for rejected requests
